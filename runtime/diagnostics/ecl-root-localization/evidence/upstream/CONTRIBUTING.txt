
* Reporting issues

When submitting bug reports try to include the following information:

- hardware and architecture
- operating system
- ECL version, commit and build flags
- how you installed ECL (your own build? package manager? roswell?)
- minimal reproducible test case
- expected and observed results
- relevant console transcript and other useful information

Some of this information can be obtained directly in the ECL repl using the form
available in this template:

#+begin_src md
Describe the problem here.

```common-lisp
(provide-some-code-reproducing-bug/issue)
```

Describe expected result and what output you got.

Provide details regarding ECL version (or preferably commit), operating system and if relevant the build options and versions of the build tools.
```common-lisp
(format t "~&~@{~12@A ~S~%~}"
        :version (lisp-implementation-version)
        :vcs-id (ext:lisp-implementation-vcs-id)
        :os (software-type)
        :os-version (software-version)
        :machine-type (machine-type)
        :features *features*)

```

Some additional notes.
#+end_src

Before releasing ECL we often ask the community to help with testing. In that
case a separate ticket is opened in the repository that describes the current
testing and release status. Please include testing results in comments in such
threads.

* Submitting code, documentation, tests and changes 

When you contribute changes to the repository keep in mind that all submitted
material is considered to be licensed under the same terms as the rest of the
work. Notably the core is licensed under LGPL-2.1-or-later and examples are
licensed under BSD-2-Clause. For detailed information see the file LICENSE.
Per-file copyright and license headers are extraneous and should not be included
in new code. There is no need to sign a contribution license agreement.

Always make a new branch based on the current ~develop~ branch from the main
repository. After adding your changes, make a merge request against that
branch. To aid easy bisecting after each commit the repository should be in a
working state. Keep changes focused in a branch, if there are two independent
features developed then make two pull requests.

When feasible, before addressing an issue write a commit containing a regression
test that demonstrates the problem by failing. In a separate commit introduce
the change that fixes your failing test. Before claiming that the merge request
is ready for merging make sure that there are no regressions in our internal
tests and in the ansi-test suite (~make check~ and ~make ansi-test~).

When introducing new features, the pull request should be accompanied with
appropriate changes to the manual. If the change is noteworthy, add an entry to
the file CHANGELOG.

* LLM usage policy

The legal status of code generated with LLM is uncertain, this is why ECL does
not currently accept contributions written with these tools. When the copyright
law catches up with the technology, we may revise this policy. We also expect
that all messages in discussions are written by a person and not generated. In
general assets generated by LLMs are in ECL treated as being proprietary. Mere
reviewing and understanding the code is not enough for the code to be accepted.

That said, we do not prescribe contributor tooling. It is fine to use LLMs to
analyze the codebase and help the programmer with debugging it. It is also fine
to proofread human-written messages for errors and typos and to lint code that
you have written.

Please keep in mind that we are not the police and there won't be any witch
hunts. We expect contributors to be honest about their contributions. Only when
there is compelling evidence that changes were generated by an LLM they will be
rejected (notably "It looks to me like AI" does not count as a valid reason).
If you happen to fix a bug or implement a feature using an LLM, then a proper
way to alleviate that is to rewrite changes from scratch in a fresh checkout
based on understanding of the issue (not based on the preexisting LLM code).
