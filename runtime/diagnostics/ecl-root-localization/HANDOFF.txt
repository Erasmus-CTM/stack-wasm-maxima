Established evidence
--------------------
1. The standalone C collector fixture uses real BDWGC APIs and private headers
   to OBSERVE occupancy. It deliberately queues valid zero-containing ranges
   until two mark-stack entries remain, then invokes modeled ECL-style scanning.
   Additional lazy pushes abort with SIGABRT and "Unexpected mark stack overflow".
   This is a synthetic capacity precondition, not a natural ECL workload.

2. GC_push_all's own source comment says it should be used only when mark-stack
   overflow is impossible. It adds a descriptor and aborts at the current limit.
   GC_push_conditional(...,1) usually delegates to GC_push_all; inspect platform
   and PROC_VDB/auto-incremental branches rather than assuming universal behavior.

3. GC_push_roots invokes GC_push_other_roots after register/C-stack traversal.
   Its source explicitly cautions that the callback must handle possible overflow.
   This provides a plausible entry-pressure mechanism, not proof of the browser
   failure's caller or of natural reachability in ECL.

4. Native 32-bit and 64-bit runs of the existing fixture passed their expected
   controls: 16 cases per width, including four expected aborts per width. Eager
   scanning retained atomic referents without capacity growth. Separate pointerful
   cases exercised BDWGC's ordinary recoverable worklist growth. No collector code,
   initial capacity or growth algorithm was patched.

5. The downstream target-only ECL patch replaces seven GC_push_all calls and one
   locked-cblock GC_push_conditional(...,1) call with GC_push_all_eager. It preserves
   bounds, null guards, locked-cblock mark bits and the previous callback. Native
   host ECL is built from pristine source before applying the target overlay.
   The inspected upstream revision has one additional ecl_core range, so the fork
   patch must not be applied blindly to current upstream.

Important limits
----------------
* The standalone fixture does NOT execute ECL's actual scanner.
* No ECL-only reproducer is established yet.
* The exact caller responsible for the original browser abort remains unproven.
* Fixing ECL-owned ranges does not fix an unsafe unchanged previous callback;
  the fixture explicitly demonstrates that limitation.
* Eager scanning retains an unregistered interior-pointer control that lazy
  scanning rejects. Equal retention, memory use and finalizer timing are unproven.
* Native 32/64-bit results do not themselves establish Wasm32 behavior.
* Incremental-enabled fixture runs perform full collections; they do not cover
  mutations between incremental marking steps.
* Passing downstream browser/parity tests does not retrospectively prove the
  original failure mechanism.

Prepared, UNEXECUTED actual-ECL candidate
---------------------------------------
Source inspection suggests a simpler route than synthetic mark-stack prefill:

SI:LOAD-FOREIGN-MODULE opens and locks a library cblock. stacks_scanner queues a
range for each locked library in cl_core.libraries. Loading many DISTINCT inert
local shared libraries may therefore exercise the real ECL scanner's descriptor
capacity without direct collector calls or callback replacement.

The pinned library loader also deduplicates by library handle. Use a SAME-PATH
repeated-load control as well as distinct-file copies, and verify actual unique
locked-cblock counts rather than assuming each load added a new one.

Suggested research sequence
---------------------------
1. Independently review the source paths and candidate assumptions. Keep actual
   ECL integration separate from the already established synthetic collector test.
2. Obtain/build an unmodified, precisely identified ECL. A distribution ECL can
   provide preliminary evidence, but cannot substitute for the pinned fork or
   current upstream. Record complete host/build/compiler/collector information.
3. Establish a small successful load/collection control. Then compare repeated
   loads of one library against distinct inert local libraries in fresh processes.
   Use bounded runtimes and preserve stdout/stderr, exit status and resource limits.
4. If an abort occurs, capture a debugger backtrace and identify the precise
   root-push call, actual mark-stack occupancy/capacity and number of locked
   libraries/environments. Bisect the count needed to reproduce.
5. Distinguish ECL scanner overflow from OS loader limits, collector dynamic-root
   registration limits, ordinary recoverable object-worklist overflow and timeout.
   The error text alone does not prove the ECL scanner is responsible.
6. Test pristine versus eager-scanning variants only AFTER establishing the
   unmodified baseline. Do not enlarge/shrink collector limits to manufacture
   the desired result. Check retention consequences separately.
7. If library loading does not reproduce, retain that negative result. Investigate
   natural pointerful C-stack pressure before callback entry, and normal ECL
   environment/thread roots, without starting from synthetic collector prefill.
8. Reduce any positive result to attached C/shell/Lisp files plus exact commands
   that require neither Python nor our repository. Include observed logs, expected
   behavior and a clear statement about which actual ECL callback was exercised.
